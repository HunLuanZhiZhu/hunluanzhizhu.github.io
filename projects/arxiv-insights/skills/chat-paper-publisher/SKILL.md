# arXiv 暂存论文 · 普通聊天人工授权发布

## 一、调用边界

本 Skill **只适用于普通聊天中的独立发布请求**，不属于 `hourly-paper-pipeline` 的自动生产步骤。读取本文件不构成发布授权；仅当用户在当前普通对话中明确要求“发布／推送／提交”具体论文或全部可访问草稿时，才可写入 GitHub。用户仅要求设计、解释、检查或修改 Skill 时，不得借此发布论文。不可自行创建、修改、暂停定时任务。所有仓库操作通过 GitHub 插件，不操作本地仓库、不启动发布脚本或监控服务。

在执行前，使用 GitHub 插件读取根 `AGENTS.md`、`projects/arxiv-insights/README.md`、`projects/arxiv-insights/skills/hourly-paper-pipeline/SKILL.md`、`projects/arxiv-insights/skills/paper-html-explainer/SKILL.md` 和 `projects/arxiv-insights/tools/build_paper_index.py`，必要时读取更近的仓库指令。以当前远程版本为准；冲突时先澄清。只修改授权的论文页面，不顺带调整其他项目或索引程序。

## 二、确定发布集合与原始文件

1. 根据用户授权范围列出当前会话及可访问历史中的 HTML 附件；使用文件工具查找、读取完整字节或内容，不得凭先前消息中的沙盒链接推测文件仍可访问。逐项记录原附件名称、稳定 arXiv ID、版本和来源。
2. “全部”指**当前实际可取得且可核实的全部未发布草稿**，不是声称穷尽不可访问的历史会话。列出无法取得、损坏或缺少来源的项目；不可用记忆重建附件冒充原稿。
3. 使用 GitHub 插件逐个读取 `projects/arxiv-insights/papers/<稳定-id>/index.html` 判断是否已存在；版本号 `v1/v2` 不属于稳定 ID。远程已存在时默认跳过，不覆盖、不重置 `added_at`；如用户明确要求更新，则另行对比差异并遵守首次收录时间不可变。
4. 同批 ID 重复时暂停该 ID，核对来源及版本，不通过“最后一个覆盖前一个”处理。每篇都必须拥有独立且完整的 HTML。

## 三、发布前逐篇自检（调用专用 Python 脚本）

**在第一笔写入前完成本批所有候选的检查**，避免写入一半才发现基本格式错误。逐篇解析 HTML 的唯一 `<script type="application/json" id="paper-meta">`，确保在 `<head>` 内且 JSON 为对象。至少核验：

- `arxiv_id` 与目录名完全相符；`title`、`title_zh`、`summary`、`heat_note` 均为真实非空字符串；`topics` 为非空字符串数组。
- `published` 为经原始论文核实的首次发表日，**严格为合法 `YYYY-MM-DD`**，不能是 `2026-10-13T20:25:59Z` 等完整时间戳。
- `date` 为本站实际归档日，严格为合法 `YYYY-MM-DD`，不可为 `null`、`YYYY-MM-DD` 等草稿占位；使用约定时区计算实际日历日期，不直接照抄论文发表日。
- `added_at` 为首次正式收录的真实 UTC ISO 8601 时间，必须以 `Z` 结尾；首次发布时在实际操作阶段赋值，后续修改不得覆盖。不要把草稿生成时间当收录时间。
- 无剩余模板占位、明显错误链接或指向不存在的本地资源；正文的公式、原文来源、专属 SVG、交互、中文术语、手机与桌面验收须有可核查记录。缺失的浏览器验收必须如实标记，不能声称已通过。
- 参考 `build_paper_index.py` **当前实际字段规则**逐项检查，尤其严格校验日期正则与真实日历有效性、字符串类型、时间戳时区、必填字段。不能仅凭 JSON 可解析或 HTML 可打开就放行。

**普通聊天发布时必须主动读取并调用** `projects/arxiv-insights/tools/preflight_papers.py`，将待提交的最终 HTML 内容保存为临时文件并执行：

```bash
python projects/arxiv-insights/tools/preflight_papers.py --mode publish /tmp/papers/2610.19159/index.html
# 多篇：在命令末尾追加多个 HTML 路径
# 只读检查仓库现有论文（可选）：
python projects/arxiv-insights/tools/preflight_papers.py --mode publish --all
```

脚本只读，不提交、不写索引、不作为 Git Hook 或 CI 强制门禁；退出码 0 表示元数据检查通过，非零表示存在错误。**若当前普通聊天环境无法执行 Python，须明确报告未执行，不得声称自检通过，也不得跳过验证后直接发布；应请求用户提供可执行环境或授权采用等价的逐字段验证方式。** 脚本不能验证论文事实真实性、浏览器渲染或远程去重，仍须执行本节其他核查。**不读取或手工编辑 `data/papers.json`**。若远程规范或现有索引程序要求更多字段，必须满足更严格的现行约束。任何候选不合格，记录原因并跳过该篇；其他合格篇是否继续，按用户批量授权及风险判断执行，不隐瞒部分成功。

## 四、预发布整理和提交

1. 保留原始正文、交互及学术数据，只对必要的元数据和已确认的链接错误做最小修复；不擅自改写论文结论。发布前再次解析**最终将提交的完整 HTML**，重新逐字段检查，特别是 `published`、`date`、`added_at`。
2. 记录每篇最终路径、内容摘要或哈希、目标分支及发布元数据；确保文件内容未截断。用户授权一次批量发布，可分多笔 GitHub API 提交，但每笔都必须可追踪。不要声称多笔提交为单一原子事务。
3. 使用 GitHub 插件创建新文件；若远程路径在检查后被其他人创建，停止该篇并重新核查，不覆盖。若是用户明确授权的更新，先取得最新 blob SHA 再更新。
4. 每笔提交后，通过 GitHub 插件重新读取远程文件并核对元数据和正文完整性。记录成功、跳过、失败和提交 SHA；不得因为某篇失败而重复创建已成功的篇目。

## 五、索引与 Pages 验收

提交成功**不等于**索引生成或网页部署成功。查找 `.github/workflows/arxiv-paper-index.yml` 对应的 GitHub Actions 运行，优先检查最新提交关联的运行；读取作业步骤及失败日志，确认 `Build index from HTML` 成功，随后核查索引提交是否完成。必要时等待运行结束再判断，不能用通知邮件或初始排队状态代替最终结论。

如果索引失败：读取具体报错和涉及文件，区分本批新文件与历史文件问题；只在原用户授权范围内修正明确错误，并再次执行元数据核验、提交和工作流检查。不要未经授权改动索引脚本或其他历史文章；不要把重新运行工作流当作修复内容错误的方法。对连续失败、权限不足或原因不明的情况停止自动修复并报告。

确认索引成功后，检查 GitHub Pages 构建与线上页面实际可访问性；若没有权限或浏览器能力，则明确标记“未验证”，不得写“全部上线”。不要手工改写 `data/papers.json`；由仓库现有 Actions 生成。若 Actions 自动写入权限异常，报告并等待用户另行授权修复工作流。

## 六、失败恢复与结果报告

逐篇输出：论文 ID、标题、原附件、目标路径、校验结果、提交状态与 SHA、远程回读结果；批次输出：候选数、成功数、跳过数、失败数、索引运行状态、Pages 可访问状态及未解决问题。准确区分：**附件可访问 → 发布前合格 → GitHub 文件已提交 → 索引已生成 → Pages 已上线** 五个阶段。

部分提交成功时，保留已成功文件，后续重试只处理尚未成功或明确授权修复的文件；不强推、不回滚用户其他修改、不覆盖已存在论文。不可访问的附件、未完成的浏览器验收、失败日志和权限限制必须明确报告。不得声称任务已全量完成，除非每一项都得到独立验证。

## 七、与自动生产任务的隔离

本 Skill 不改变自动任务边界：定时生产仍然只读 GitHub、每轮最多一篇、生成并交付 ChatGPT 附件，不发布、不读取或修改 `data/papers.json`。本 Skill 的存在不构成永久发布授权；每次普通聊天发布均需用户明确指示。仅在用户要求时才编辑本 Skill 本身。
