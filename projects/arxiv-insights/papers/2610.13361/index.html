AgentSWE 的问题

给编程智能体自然语言委托，让它自己造、改或优化一个智能体，冻结交付物，再在未见案例上运行。

评价对象：造智能体的能力

这里的“委托”不是有标准答案的填空题。用户只规定目标、运行接口、限制和资源，实现方案由编程智能体自己选择。因此，评测不能只检查源码长得像不像答案，而要实际运行它交付的系统。

02 / 前置知识

先弄清四个概念

① 智能体与执行框架分别是什么？

智能体（Agent）是将语言模型、工具、状态与控制逻辑组成的可运行程序。执行框架（Harness）负责规划、工具路由、重试、上下文管理和结果校验。输入是任务与环境，输出是可观察的操作及产物。本文比较的“编程智能体”还要编写另一套这样的程序，所以存在“造系统者”和“被造系统”两层。

② 开发案例与隐藏验收为什么要分开？

开发集（Development Cases）是编程智能体能反复查看和试错的样例；隐藏验收集（Held-out Cases）在交付冻结后才运行，用来检验能否覆盖需求中没有被示例展示的情况。输入是同一委托的不同实例，输出是各自的行为评分。两者差距可暴露针对可见样例的过拟合。

③ 什么是硬门槛与细则评分？

硬门槛（Validity Gate）是不可协商的有效性要求，例如必须成功启动、按约定格式交付且未越权。失败直接记零；通过后才由按需求制定的评分细则（Rubric）评估行为完整性，可能给部分分。输入是运行日志、交付物和状态；输出是有效性标志及 0–100 的任务分数。

④ 为什么要固定运行时模型？

被造智能体使用的语言模型会影响成绩。论文让同类任务中的交付物通过评测方控制的统一模型入口运行，尽量把差异归因于编程智能体编写的提示、工具编排和状态逻辑。输入是冻结代码与固定模型接口，输出是可比较的运行轨迹；这不能消除模型采样随机性。

04 / 数学

技术拆解：怎样把“符合需求”写成可测量的量？

下列公式对应论文第 3 节的定义与公式（1）—（3）。采用浏览器原生数学标记语言（MathML）实际排版，每式下方保留 LaTeX 源码，方便逐字符核对。

式 A · 自然语言需求的四元组（论文 §3.1）

q=(g,I,C,R)

LaTeX 源：q=(g,I,C,R)

符号全解：q 是一项自然语言委托；g 是目标及成功定义；I 是启动、输入输出及交付物的接口契约；C 是允许修改或调用内容的约束；R 是数据、仓库、模型和搜索等资源；括号表示有序组合。它把“给我做个好用的智能体”拆成可验收的承诺。

式 B · 编程智能体生成交付物（论文 §3.1）

a^∼β(q,a0,D;B)

LaTeX 源：\hat a\sim\beta(q,a_0,D;B)

符号全解：â（带帽的 a）是最终交付的智能体；β 是负责开发的编程智能体；q 是式 A 的委托；a₀ 是初始产物（创建时为空，编辑时为现有代码，优化时为可运行系统）；D 是公开开发案例集合；B 是时间与计算预算；∼ 表示生成过程具有随机性；分号区分预算条件。交付的智能体本身由执行框架 h 和运行时模型 m 构成，即 a=(h,m)（论文 §3.1）。

式 C · 需求忠实度（论文公式 1）

F(a^;q)=V(a^)·𝔼x∼Xq𝔼y∼a^(x;E)[μq(x,y)]

LaTeX 源：F(\hat a;q)=V(\hat a)\cdot\mathbb E_{x\sim X_q}\mathbb E_{y\sim\hat a(x;E)}[\mu_q(x,y)]

符号全解：F(â;q) 是交付智能体 â 对需求 q 的忠实度，取值 0 至 1；V(â) 是有效性门槛，值为 0 或 1；x 是某个具体任务实例，X_q 是需求 q 所涵盖的实例分布或空间；E 是运行环境；y 是智能体在 x 和 E 下产生的可观察结果，y∼â(x;E) 表示随机运行结果；μ_q(x,y) 是该结果满足需求的程度，范围 0 至 1；两个 𝔼 是先对实例、再对运行随机性求期望；方括号表示被平均的评分。关键：即使结果看似优秀，只要有效性门槛为 0，整体忠实度就是 0。

式 D · 编辑必须兼顾新增与回归（论文公式 2）

μq=μnew∧μreg

LaTeX 源：\mu_q=\mu_{\mathrm{new}}\wedge\mu_{\mathrm{reg}}

符号全解：μ_q 是编辑任务的整体需求满足条件；μ_new（new：新增）表示新能力满足程度或条件；μ_reg（reg：回归）表示旧功能没有被破坏的条件；∧ 是逻辑合取，即两方面必须同时满足。论文用这一逻辑约束强调：只把新功能做出来，却破坏原有行为，不算完整交付。这里不擅自把合取解释为数值相乘。

式 E · 优化的剩余差距缩小率（论文公式 3）

γ(a^)=min{1,J(a^)−J(a0)J⋆−J(a0)}

LaTeX 源：\gamma(\hat a)=\min\{1,\frac{J(\hat a)-J(a_0)}{J^\star-J(a_0)}\}

符号全解：γ(â) 是交付智能体相对于初始产物的目标差距缩小比例；J(a) 是智能体 a 在固定隐藏实例上的原生目标分数（0–100，越高越好）；â 是优化后交付物；a₀ 是原始系统；J⋆ 是目标上限，本文取 100；min 是取较小值，1 将正向收益封顶在 100%，但负收益仍可为负；分子是改进量，分母是原系统距满分的剩余空间。若 J(a₀)=100 则分母为零，教学演示避免该情形；论文实际任务有剩余改进空间。

式 F · 开发—验收差距（论文 §3.2，符号化定义）

Δ=FD−FD¯

LaTeX 源：\Delta=F_D-F_{\bar D}

符号全解：Δ 是开发与隐藏验收之间的分数差；F_D 是在公开开发案例集合 D 上估计的忠实度；F_D̄ 是在不与 D 重叠的隐藏案例集合 D̄ 上估计的忠实度；减号表示前者减后者。较大的正差距意味着可见样例表现比真正交付表现好，可能由过拟合、需求遗漏或执行失败造成，并非单独证明某一种原因。

07 / 批判阅读

如何正确解读低分？

作者结论

在这 25 项委托和指定评测条件下，编程智能体往往只能部分满足需求；更好的验证方式应围绕需求条款、真实运行与未见实例，而不是仅检查代码或自述完成。

证据边界

主要模型—任务配对仅构建一次，随机波动不可忽略；创建与编辑采用模型裁判评分，可能继承裁判误差或模型家族偏差；不同任务家族的运行模型与裁判不同，绝对分数不能跨类直接比较（附录 J）。

还有两点值得谨慎：一是需求材料部分由生成式模型草拟，再由作者核实修改，任务难度与需求表达方式可能影响结果；二是“用户真正想要的东西”本身并非完全客观，论文通过需求细则、执行轨迹和门槛近似测量，而不是从哲学上解决了意图对齐。

本站判断：AgentSWE 的核心价值是改变评测对象——从“写了什么代码”转向“交付物在未见情形下做了什么”。低分是研究中的实证警示，不意味着任何特定商业编程智能体在所有真实场景下都只有这些分数。
